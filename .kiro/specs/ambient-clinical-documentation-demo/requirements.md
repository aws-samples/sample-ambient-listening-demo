# Requirements Document

## Introduction

This document defines the requirements for the Ambient Clinical Documentation Demo — a hands-on workshop project that demonstrates end-to-end ambient clinical documentation using Amazon Connect Health integrated with OpenEMR deployed on AWS ECS. The demo enables healthcare technology developers and AWS solution architects to experience the complete flow from EHR patient data retrieval through ambient audio listening to structured clinical note generation.

## Glossary

- **Demo_Application**: The web application (React/Next.js frontend with backend service) that provides the clinician-facing UI for the ambient documentation workflow
- **OpenEMR_Stack**: The OpenEMR open-source EHR system deployed on AWS ECS Fargate using the openemr-on-ecs CDK stack, including Aurora Serverless v2, ElastiCache, and EFS
- **FHIR_API**: The FHIR R4 API exposed by OpenEMR for reading and writing patient clinical data
- **Ambient_Service**: The Amazon Connect Health ambient documentation service accessed via the StartMedicalScribeListeningSession API using HTTP/2 streaming
- **Clinical_Note**: The structured clinical documentation output (SOAP format) generated by the Ambient_Service after a session ends
- **Evidence_Map**: The mapping that links individual statements in the Clinical_Note back to specific moments in the session transcript
- **After_Visit_Summary**: A patient-friendly summary of the encounter generated by the Ambient_Service
- **Transcript**: The real-time and final text output of the audio session with speaker diarization (CLINICIAN vs PATIENT)
- **Workshop_Participant**: A healthcare technology developer or AWS solution architect following the workshop instructions
- **Patient_Context**: Structured patient information retrieved from the FHIR_API and provided to the Ambient_Service via encounterContext.unstructuredContext (up to 10KB)
- **Audio_Stream**: FLAC or PCM encoded audio (16-bit, 16000 Hz minimum sample rate) streamed to the Ambient_Service via HTTP/2
- **Session**: A single ambient documentation session managed through the Ambient_Service lifecycle (domain, subscription, session creation, streaming, and completion)

## Requirements

### Requirement 1: Infrastructure Deployment

**User Story:** As a Workshop_Participant, I want to deploy the complete infrastructure stack using CDK, so that I have a working OpenEMR instance and supporting AWS services for the demo.

#### Acceptance Criteria

1. WHEN the Workshop_Participant runs the CDK deployment command, THE OpenEMR_Stack SHALL deploy OpenEMR on ECS Fargate with Aurora Serverless v2, ElastiCache, and EFS within 45 minutes
2. WHEN the OpenEMR_Stack deployment completes, THE OpenEMR_Stack SHALL expose the FHIR_API endpoint over HTTPS that responds to a FHIR metadata request with a valid CapabilityStatement resource
3. WHEN the OpenEMR_Stack deployment completes, THE OpenEMR_Stack SHALL output as CDK stack outputs the FHIR_API base URL, the OpenEMR web console URL, and the credentials required for Demo_Application configuration
4. IF the Workshop_Participant specifies a target AWS region other than us-east-1 or us-west-2, THEN THE OpenEMR_Stack SHALL fail deployment with an error message indicating the supported regions
5. IF the CDK deployment command fails, THEN THE OpenEMR_Stack SHALL output the failure reason and leave no partially-provisioned resources that incur cost

### Requirement 2: Synthetic Patient Data Loading with Synthea

**User Story:** As a Workshop_Participant, I want to load Synthea-generated synthetic patient data for 100 patients into OpenEMR, so that I have realistic patient records available for the ambient documentation demo.

#### Acceptance Criteria

1. THE Demo_Application repository SHALL include instructions or a script to generate 100 synthetic patient records using Synthea in FHIR R4 Bundle format
2. WHEN the data loading script is executed, THE Demo_Application SHALL load the 100 Synthea-generated patient bundles into the OpenEMR_Stack via the FHIR_API and complete loading within 30 minutes
3. WHEN synthetic data loading completes, THE FHIR_API SHALL return patient demographics for each loaded patient, and conditions, medications, allergies, and encounters for patients where Synthea generated those resource types
4. IF the FHIR_API rejects a Synthea-generated record, THEN THE Demo_Application SHALL log the rejection reason to standard output including the patient bundle filename and continue loading remaining records
5. THE workshop guide SHALL document the Synthea configuration parameters used to generate the patient population
6. WHEN the data loading script completes, THE Demo_Application SHALL print a summary reporting the total number of patients successfully loaded and the total number of patients that failed to load
7. IF the FHIR_API is unreachable when the data loading script starts, THEN THE Demo_Application SHALL exit with an error message indicating the FHIR_API endpoint is unavailable

### Requirement 3: Patient Context Retrieval

**User Story:** As a Workshop_Participant, I want the demo application to pull patient context from OpenEMR, so that the ambient session has relevant clinical background for note generation.

#### Acceptance Criteria

1. WHEN a Workshop_Participant selects a patient in the Demo_Application, THE Demo_Application SHALL retrieve patient demographics, active conditions, current medications, and known allergies from the FHIR_API within 10 seconds
2. IF the retrieved patient data exceeds 10KB when formatted, THEN THE Demo_Application SHALL truncate the Patient_Context to 10KB by prioritizing demographics first, then allergies, then medications, then conditions
3. WHEN patient data retrieval completes successfully, THE Demo_Application SHALL display the formatted Patient_Context in the clinician-facing UI before allowing session start
4. IF the FHIR_API does not respond within 10 seconds, THEN THE Demo_Application SHALL display an error message indicating the EHR connection failure
5. IF the FHIR_API returns an error for one or more resource types but succeeds for at least one, THEN THE Demo_Application SHALL display the successfully retrieved data and show a warning indicating which resource types could not be loaded

### Requirement 4: Ambient Session Management

**User Story:** As a Workshop_Participant, I want the demo to manage the full ambient session lifecycle, so that I can observe how domain, subscription, and session resources are created and used.

#### Acceptance Criteria

1. WHEN the Demo_Application starts, THE Demo_Application SHALL create or reuse an Ambient_Service domain and subscription, identifying an existing domain by matching domain name
2. WHEN a Workshop_Participant initiates a session, THE Demo_Application SHALL create a Session with the Ambient_Service including the Patient_Context in encounterContext.unstructuredContext within 30 seconds of the initiation request
3. WHEN a Session is created, THE Demo_Application SHALL configure two channel definitions with CLINICIAN assigned to channel 0 and PATIENT assigned to channel 1
4. WHEN a Workshop_Participant ends a session, THE Demo_Application SHALL send a session end event to the Ambient_Service and display a confirmation indicating the session has ended
5. IF Session creation or domain/subscription creation fails, THEN THE Demo_Application SHALL display the error details including the failure stage (domain, subscription, or session) and suggest corrective actions
6. WHILE the session lifecycle is progressing, THE Demo_Application SHALL display the current lifecycle stage (domain setup, subscription setup, session creation, active session, session ended) in the clinician-facing UI

### Requirement 5: Audio Streaming

**User Story:** As a Workshop_Participant, I want to stream audio from a microphone or pre-recorded file to the ambient service, so that I can observe real-time clinical conversation processing.

#### Acceptance Criteria

1. WHEN a Workshop_Participant starts audio capture, THE Demo_Application SHALL stream audio to the Ambient_Service using HTTP/2 via the StartMedicalScribeListeningSession API
2. THE Demo_Application SHALL encode audio as PCM at 16-bit depth with a minimum 16000 Hz sample rate
3. THE Demo_Application SHALL support audio input from the browser microphone
4. THE Demo_Application SHALL support audio input from a pre-recorded WAV audio file (PCM 16-bit, 16000 Hz) for repeatable demonstrations
5. WHEN audio streaming is active, THE Demo_Application SHALL display a visual indicator showing that audio is being captured and streamed
6. IF the HTTP/2 stream connection drops or no data is received for 30 seconds, THEN THE Demo_Application SHALL notify the Workshop_Participant and provide an option to restart the session
7. IF the browser denies microphone permission, THEN THE Demo_Application SHALL display an error message instructing the Workshop_Participant to grant microphone access

### Requirement 6: Real-Time Transcription Display

**User Story:** As a Workshop_Participant, I want to see the conversation transcribed in real time with speaker labels, so that I can observe the diarization and transcription quality.

#### Acceptance Criteria

1. WHILE audio streaming is active, THE Demo_Application SHALL display Transcript segments within 2 seconds of receiving them from the Ambient_Service
2. THE Demo_Application SHALL label each Transcript segment with the speaker role (CLINICIAN or PATIENT)
3. THE Demo_Application SHALL visually distinguish CLINICIAN segments from PATIENT segments such that a user can identify the speaker of each segment without reading the label text alone (e.g., by color, alignment, or background)
4. WHILE new Transcript segments arrive, THE Demo_Application SHALL auto-scroll the transcript view to keep the most recent segment visible
5. IF a Transcript segment arrives without a speaker role attribution, THEN THE Demo_Application SHALL display the segment labeled as UNKNOWN speaker

### Requirement 7: Clinical Note Generation and Display

**User Story:** As a Workshop_Participant, I want to see the structured clinical note generated after the session ends, so that I can evaluate the quality of ambient documentation output.

#### Acceptance Criteria

1. WHEN a Session ends, THE Demo_Application SHALL retrieve the Clinical_Note from the Ambient_Service output location in S3
2. WHEN the Clinical_Note is retrieved, THE Demo_Application SHALL display the Clinical_Note in SOAP format with each section preceded by its heading (Subjective, Objective, Assessment, Plan)
3. WHEN the Clinical_Note is displayed, THE Demo_Application SHALL also display the Evidence_Map linking note statements to Transcript moments
4. WHEN a Workshop_Participant selects a statement in the Clinical_Note, THE Demo_Application SHALL scroll the Transcript view to the corresponding moment and visually highlight the referenced Transcript segment
5. IF the Clinical_Note is not available within 60 seconds of session end, THEN THE Demo_Application SHALL display a loading indicator and retry retrieval up to 3 times at 10-second intervals
6. IF all retrieval retries are exhausted without obtaining the Clinical_Note, THEN THE Demo_Application SHALL display an error message indicating that note generation failed and provide an option to retry manually

### Requirement 8: After-Visit Summary Display

**User Story:** As a Workshop_Participant, I want to see the patient-friendly after-visit summary, so that I can understand how the system produces patient-facing documentation.

#### Acceptance Criteria

1. WHEN a Session ends, THE Demo_Application SHALL retrieve the After_Visit_Summary from the Ambient_Service output location in S3 and display a loading indicator during retrieval
2. THE Demo_Application SHALL display the After_Visit_Summary in a separate tab or panel from the Clinical_Note
3. THE Demo_Application SHALL render the After_Visit_Summary content as received from the Ambient_Service without modification, preserving its patient-friendly plain language format
4. IF the After_Visit_Summary is not available within 60 seconds of session end, THEN THE Demo_Application SHALL retry retrieval and display a message indicating the summary is still being generated
5. IF the After_Visit_Summary retrieval fails after retry, THEN THE Demo_Application SHALL display an error message indicating the summary could not be loaded

### Requirement 9: Workshop Documentation

**User Story:** As a Workshop_Participant, I want step-by-step instructions covering the entire setup and demo flow, so that I can independently deploy and run the demo.

#### Acceptance Criteria

1. THE Demo_Application repository SHALL include a workshop guide with sequential numbered steps covering infrastructure deployment, data loading, application configuration, and demo execution, where each major section includes a verification command or expected output that confirms successful completion before proceeding to the next section
2. THE workshop guide SHALL document all prerequisite AWS permissions as specific IAM policy actions, CLI tools with minimum version numbers, and account configurations required before beginning the workshop
3. THE workshop guide SHALL include troubleshooting guidance for at least 5 deployment and runtime failure scenarios, each documenting the symptom, likely cause, and resolution steps
4. THE workshop guide SHALL document estimated hourly costs for the deployed infrastructure and include a teardown section with commands to remove all deployed resources, followed by a verification step confirming no billable resources remain
5. THE workshop guide SHALL provide an estimated completion time for each major section of the workshop

### Requirement 10: Demo Application Deployment

**User Story:** As a Workshop_Participant, I want to deploy the demo web application with a single command, so that I can quickly get the frontend and backend running.

#### Acceptance Criteria

1. WHEN the Workshop_Participant runs the application deployment command, THE Demo_Application SHALL deploy the frontend and backend services to AWS and complete within 15 minutes
2. WHEN deployment completes successfully, THE Demo_Application SHALL output the application URL and be accessible via a web browser over HTTPS, returning an HTTP 200 response on the root URL within 5 minutes of deployment completion
3. THE Demo_Application SHALL connect to the OpenEMR_Stack FHIR_API using configuration values from the infrastructure deployment outputs and verify connectivity by performing a FHIR metadata request on startup
4. IF required environment variables are missing, THEN THE Demo_Application SHALL exit with a non-zero status and print an error message listing each missing variable by name
5. IF the deployment command fails, THEN THE Demo_Application SHALL output the failure reason and exit with a non-zero status without leaving partially deployed resources running

### Requirement 11: Audio Language and Region Constraints

**User Story:** As a Workshop_Participant, I want the demo to enforce supported language and region constraints, so that I avoid configuration errors with the ambient service.

#### Acceptance Criteria

1. THE Demo_Application SHALL configure the Ambient_Service session for US English (en-US) language only
2. THE Demo_Application SHALL validate that the configured AWS region is us-east-1 or us-west-2 before attempting session creation
3. IF the configured region is not supported, THEN THE Demo_Application SHALL block session creation and display an error message specifying the supported regions

### Requirement 12: OpenEMR Deployment Code Updates

**User Story:** As a Workshop_Participant, I want the demo to reference the latest openemr-on-ecs CDK stack, so that I benefit from upstream fixes and improvements without manual code synchronization.

#### Acceptance Criteria

1. THE Demo_Application repository SHALL reference the openemr-on-ecs CDK stack as a Git submodule pinned to a specific release tag with the tag version documented in the repository README
2. WHEN a new version of the openemr-on-ecs repository is released, THE workshop guide SHALL document the procedure to update the pinned reference
3. THE Demo_Application repository SHALL include a compatibility verification script that runs CDK synth on the submodule and confirms the expected stack output keys (FHIR_API base URL, OpenEMR web console URL, credentials secret ARN) are present
4. IF the compatibility verification script fails, THEN THE script SHALL exit with a non-zero status and print which expected output keys are missing or which CDK synth errors occurred

### Requirement 13: Security and HIPAA Best Practices

**User Story:** As a Workshop_Participant, I want the demo infrastructure to follow security and HIPAA best practices, so that I can use this as a reference architecture for production healthcare deployments.

#### Acceptance Criteria

1. THE OpenEMR_Stack and Demo_Application CDK stacks SHALL NOT create any security group rules allowing inbound traffic from 0.0.0.0/0 or ::/0 on any port
2. THE Demo_Application ALB SHALL accept inbound HTTPS (port 443) traffic only from a configurable IP CIDR range specified at deployment time
3. ALL communication between the Demo_Application and the FHIR_API SHALL use TLS 1.2 or higher
4. ALL communication between the Demo_Application and the Ambient_Service SHALL use TLS 1.2 or higher via HTTP/2
5. THE S3 bucket storing ambient documentation outputs SHALL have server-side encryption enabled (SSE-S3 or SSE-KMS), block all public access, and enforce SSL-only access via bucket policy
6. THE Aurora Serverless v2 database SHALL be deployed in private subnets with no public accessibility and encryption at rest enabled via KMS
7. THE ECS Fargate tasks SHALL run in private subnets with outbound internet access only through NAT Gateways
8. ALL secrets (database credentials, FHIR client credentials, API keys) SHALL be stored in AWS Secrets Manager and referenced by ARN, never hardcoded in source code or environment variables in plain text
9. THE Demo_Application CDK stack SHALL include cdk-nag with the HIPAA Security rule pack enabled, and deployment SHALL fail if any HIPAA-related findings are unresolved or unsuppressed with documented justification
10. THE workshop guide SHALL include a HIPAA compliance section documenting that a BAA with AWS is required for production use, that this demo uses synthetic data only, and listing the security controls implemented

### Requirement 14: Write-Back Clinical Note to OpenEMR

**User Story:** As a Workshop_Participant, I want the generated clinical note to be written back to OpenEMR, so that I can see the full round-trip documentation workflow from EHR to ambient note and back.

#### Acceptance Criteria

1. WHEN the Clinical_Note is generated, THE Demo_Application SHALL save the Clinical_Note to the patient record in OpenEMR via the FHIR_API without requiring user action, completing the write operation within 30 seconds
2. WHEN the Demo_Application saves the Clinical_Note, THE Demo_Application SHALL create a DocumentReference resource in OpenEMR containing the Clinical_Note content as a text attachment, the subject reference to the associated patient, the session date, and the encounter type
3. WHEN the write-back completes successfully, THE Demo_Application SHALL display a confirmation message indicating the note has been saved to the patient chart
4. IF the FHIR_API write operation fails, THEN THE Demo_Application SHALL display the error type and failure reason, and provide a retry option allowing up to 3 retry attempts
5. WHEN the Workshop_Participant navigates to the patient record in OpenEMR, THE written Clinical_Note SHALL be visible in the patient's document list with the session date and document title identifying it as an ambient clinical note
